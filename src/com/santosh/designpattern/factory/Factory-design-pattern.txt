Factory Method Pattern
	It defines an interface for creating objects but lets subclasses decide which object to instantiate. 
	Subclasses override the factory method to produce specific object types.
	It Supports easy addition of new product types without modifying existing code.

Example
	In a health claim application, when you need to create different types of claim objects like medical claim and dental claim, each claim type has different processing rules, validation, etc.

Advantages
	
	1.Encapsulation of Object Creation - The client code doesn’t need to know the details of how different claim objects (Medical, Dental, Vision) are created.
	
	2.Flexibility & Extensibility - Adding a new claim type (e.g., PharmacyClaim) only requires extending the factory logic, without changing existing client code.
	
	3.Improved Maintainability - Centralizing creation logic makes debugging and updates easier. If claim creation rules change, you only update the factory.


Trade-off
	
	1.Extra Layer of Abstraction - Introducing a factory adds more classes and methods, which can make the design more complex for simple use cases.
	
	2.Maintenance of Factory Logic - As the number of claim types grows, the factory itself can become bloated if not managed well (e.g., a giant switch-case).
